# Моя концепция учебного проекта

27.10.2026,0.1.1. Я решаю узкую задачу руководителя доставки: увидеть количество
заказов со сроком выбранных UTC суток по складам и не опубликовать испорченный пакет.
При сбое финальной записи предыдущий отчёт должен оставаться доступным.

Я выбрал Dagster, поскольку качество должно быть самостоятельным видимым узлом
графа с блокировкой downstream, а история успехов/ошибок должна пережить завершение
процесса. Расчёт и filesystem publication оставил обычными Python функциями.
Dagster тяжелее простого скрипта; я не добавляю webserver/daemon/Cloud или другие
платформы. После вчерашнего DuckDB я переключаю основной навык на оркестрацию assets.

| Контракт | Моё решение |
| --- | --- |
| Источник | Явно выбранный UTF8 CSV с5точными колонками,1MB/10000строк |
| Строка | Одна доставка, delivery_id уникален в пакете; WH-A/WH-B |
| Время | created/promised/delivered UTC Z с точностью до секунды,2020…2099 |
| День | promised_at попадает в выбранные UTC сутки; конец exclusive |
| Неизвестная доставка | Blank или delivered_at>=следующее00:00 даёт overdue |
| Quality | Duplicate ID и chronology — независимые blocking ERROR checks |
| Публикация | Content-addressed immutable JSON плюс atomic latest pointer |
| Повтор | Новый Dagster run, тот же отчёт используется повторно |
| Сбой | Плохой пакет не меняет latest; object-before-pointer orphan можно использовать |
| Состояние | Собственный marked workspace, Dagster SQLite journal, одна команда за раз |

Готовность я проверяю реальными runs,сохранением истории и прежнего latest,14tests,
CLI smoke и упаковкой/запуском из ZIP. Публикацию source/CI/release подтверждаю отдельно.
Примеры воспроизводимы из констант, настоящих клиентов и персональных данных нет.
Я не моделирую event ingestion, историческую видимость поступления, таймзоны складов,
SLA полноты, распределённую транзакцию, очередь или многопроцессный writer.
